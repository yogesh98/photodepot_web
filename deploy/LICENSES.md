# Photodepot account subscriptions

The Owner dashboard lives at `https://photodepot.app/admin/subscriptions`. The table reads all users from the Photodepot WorkOS environment and joins their subscriptions by immutable WorkOS user ID. New signups receive one automatic seven-day Trial, beginning at the WorkOS account creation timestamp. Email edits do not transfer access between accounts.

Owners can set Trial or Standard access for 1–3,650 days or an exact end date, extend it, revoke or restore it, reset the Mac assignment, save internal notes, record action reasons, inspect current/historical Mac assignments, and read audit history. Set starts an explicit active grant now; extend adds days from the later of now or expiry and preserves revoked status. Restore preserves the expiry date, so restoring expired access does not renew it. Optimistic revisions reject stale edits with 409. Both types expire at their exact end timestamp. Dashboard totals cover the database; user search and filters clearly cover loaded WorkOS pages. This is manual access management: no customer is charged and no billing product is enabled.

`POST /api/account/webhook` verifies WorkOS's signature over the raw bounded body and handles `user.created`. Store the endpoint secret in `WORKOS_WEBHOOK_SECRET`. The verified account callback activates the same trial as a fallback. Both atomically insert only when no subscription exists, record one `initial-trial` audit, and use the account creation date plus exactly seven days. Retries, duplicate notifications, later logins, expired trials, revocations, and manual assignments never restart the trial. Unverified accounts can have a trial record but cannot approve or receive Mac access until verified.

One subscription binds to one Mac. Reset permits a replacement Mac and invalidates earlier binding epochs and approved pairing requests. Device key history is retained for signed revoked receipts. Existing license data and public key activation remain compatible during the transition. The new desktop sign-in ships with the desktop app update; deploying the website alone cannot change installed binaries.

## Configure before deployment

These settings apply to both subscription sign-in and compatible legacy licensing.

1. Apply D1 migrations to the existing DB binding, first locally with `pnpm db:migrate:local` and then in production with `pnpm db:migrate`. Keep a private D1 backup first. `0003_subscriptions.sql`, `0004_account_devices.sql`, and `0005_account_pairings.sql` add subscription/device/pairing records and preserve legacy license, waitlist, and download data.
2. Generate the Ed25519 signing pair outside either repository:

   ```sh
   node scripts/generate-license-keypair.mjs /absolute/private/location/photodepot-license-private-key.txt
   ```

   The file contains the **base64 DER PKCS8 private key** and is created with mode 0600 without overwriting existing files. The command prints only `PHOTODEPOT_LICENSE_PUBLIC_KEY`, the public key in base64url DER SPKI format. Save the private key in a secure backup. Set the printed public key as `PHOTODEPOT_LICENSE_PUBLIC_KEY` when building the desktop app, and use `PHOTODEPOT_LICENSE_API_URL=https://photodepot.app` (the default) for that build. The desktop API origin must match this deployment.
3. Set `PHOTODEPOT_LICENSE_SIGNING_PRIVATE_KEY` as a Cloudflare Pages encrypted secret for `photodepot-web`. For example, run `pnpm exec wrangler pages secret put PHOTODEPOT_LICENSE_SIGNING_PRIVATE_KEY --project-name photodepot-web` and provide the file contents privately. Do not put it in `wrangler.jsonc`, `NEXT_PUBLIC_*`, a git-tracked file, a shell command argument, or logs.
4. Configure WorkOS AuthKit in the intended environment with the standard hosted authentication domain. Register the exact redirect URI `https://photodepot.app/api/auth/callback` and the post-sign-out return URL `https://photodepot.app/`. Use standard email/password or Magic Auth; do not enable paid custom domains, Enterprise SSO, Directory Sync, Radar, or other add-ons. [AuthKit pricing](https://workos.com/pricing) currently includes RBAC and up to 1 million monthly active users free. This migration does not enable subscription charging.
5. Create or select a dedicated Photodepot administration organization. Create the environment-level **Owner** role with the exact slug **`owner`**, leave **Member** (`member`) as the default role, and manually assign Owner to the administrator's membership in that organization. Copy that organization's ID into the application configuration. An Owner in a different organization is not authorized. Do not automatically enroll new signups into the admin organization, enable email-domain auto-enrollment, or make Owner the default. [WorkOS roles documentation](https://workos.com/docs/authkit/roles-and-permissions) explains membership role assignment.
6. Set Pages environment variables `WORKOS_CLIENT_ID`, `WORKOS_ADMIN_ORGANIZATION_ID`, and `WORKOS_REDIRECT_URI=https://photodepot.app/api/auth/callback`. Store `WORKOS_API_KEY` from the same WorkOS Production environment as an encrypted Pages secret. Generate a random `WORKOS_COOKIE_PASSWORD` of at least32 characters and store it as another encrypted secret. Login uses public PKCE; the API key is used only by server user-management APIs. Keep secrets out of `wrangler.jsonc`, `NEXT_PUBLIC_*`, Git, command arguments, logs, and desktop builds. Missing or invalid settings fail closed.
7. Leave previews unavailable for sign-in/administration unless separate staging configuration is deliberate. Every admin API and page enforces Owner membership in the dedicated organization. Account login uses separate encrypted cookies and grants no administration access. All sign-in, subscription, pairing, approval, and verification responses are `private, no-store`; keep `/account/*` in Pages Function routing. A desktop built with a test public key cannot trust production receipts.
8. Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, and `pnpm functions:build`, then deploy the backend. Production uses WorkOS as the administration login gate; the former Cloudflare Access application and settings were removed after verification. Check Owner access, Member/anonymous denial, alternate-host denial, subscription expiry/revocation, and account pairing. Desktop proof endpoints remain public and require cryptographic device signatures.
9. Test account sign-in and Trial/Standard subscriptions on a desktop build containing the matching vendor public key. Then release that desktop build through the established signing/notarization process.

For local subscription development, use `pnpm subscriptions:setup --desktop-dir /path/to/photodepot`, add WorkOS Development settings to its generated `.dev.vars.development`, and run `pnpm subscriptions:dev`. This creates an isolated local database/signing authority and matching public desktop `.env.development`; run `pnpm dev:subscriptions` in the desktop checkout. Register the exact `http://localhost:8788/api/auth/callback` callback in WorkOS Development. Production secrets are not loaded. The dashboard visibly labels Development. The admin API has no development password or bypass: an authenticated WorkOS session with the `owner` role in the configured admin organization is required. Automated integration tests use isolated authentication fixtures and never make real WorkOS calls. See the website README for setup details.

## Administration sign-in

`GET /api/auth/login` starts Owner AuthKit sign-in. `GET /api/auth/callback` validates state, PKCE, token signature, client, user, verified email, and Owner organization before storing its encrypted cookie. `POST /api/auth/logout` signs out. Visiting `/admin/subscriptions` without a session starts sign-in; expired API sessions return401.

The application validates WorkOS access tokens on every protected request and refreshes expired tokens. Role changes and WorkOS session revocation are reflected when the current access token expires and refresh checks the session. Keep the access-token duration short in WorkOS application [session settings](https://workos.com/docs/authkit/sessions). Alternate hostnames are denied when their origin differs from the configured callback, even if they receive a copied session cookie.

The dashboard's **Sign in** link opens a new tab if its session expires; return and select **Refresh**. Visible user pages refresh every 30 seconds while dialogs and writes are closed. WorkOS outages preserve the existing list and show an error; an outage is never presented as an empty account list.

## Desktop account sign-in

The desktop keeps its Ed25519 device identity and opens hosted WorkOS authentication in the external browser. WorkOS tokens stay in a browser session; the desktop receives only a signed device receipt. Existing device/receipt storage remains encrypted and may use macOS Keychain; account login does not itself remove that storage dependency.

`POST /api/account/pairing/start` accepts `{deviceId,devicePublicKey,challenge,deviceSignature}`, signed over UTF-8 `JSON.stringify(['photodepot-account-pairing-v1','start',deviceId,devicePublicKey,challenge])`. It returns `{pairingId,approvalUrl,expiresAt,expiresInMs,pollIntervalMs}`, with `expiresInMs: 600000` so the desktop can track the bounded lifetime using local elapsed time despite clock differences. The approval URL contains a separate random code; it never includes the polling identifier or any WorkOS token. Pairings expire in10 minutes. The database stores hashes of both random identifiers.

`GET /account/activate?code=…` uses ordinary verified-user WorkOS login through `/api/account/auth/login`; users need no administration membership. The initial verified callback inserts the signup trial if needed. Browser approval requires a same-origin POST and a currently active subscription. The account and binding epoch become immutable for that request. Approval never renews or replaces a subscription. Device proof is required for polling and cancellation, using `JSON.stringify(['photodepot-account-pairing-v1','poll'|'cancel',pairingId,deviceId,challenge])`.

Polling returns `{status:'pending'}` or `{status:'approved',receipt:{payload,signature}}`. Delivery can retry until the pairing expires; every delivery checks current WorkOS existence/verified email, subscription, and the approved binding epoch. Pairing approval and expiry are checked atomically with device binding: a cancellation completed before binding prevents an in-flight poll from claiming the Mac slot. Deleted/unverified accounts and inactive subscriptions cannot sign in. WorkOS outages fail closed. The receipt echoes the original app challenge, uses the stable subscription ID as `licenseId`, and caps active expiry at `min(now+48hours,subscriptionEnd)`. `/api/licenses/verify` resolves account devices before compatible legacy bindings and performs the same fresh account/subscription checks. Owner reset cannot be bypassed by replaying an older approved pairing.

## Compatible license protocol and enforcement

`POST /api/licenses/activate` accepts JSON `{key, devicePublicKey, challenge, signature}`. Keys normalize with trim/uppercase. The device public key is base64url DER SPKI Ed25519. The challenge is 32 random bytes in base64url. The device signs the UTF-8 bytes of `JSON.stringify(['photodepot-license-v1','activate',normalizedKey,devicePublicKey,challenge])`.

`POST /api/licenses/verify` accepts `{deviceId, challenge, signature}`. The device ID is lowercase hex SHA-256 of the DER SPKI bytes. The device signs `JSON.stringify(['photodepot-license-v1','verify',deviceId,challenge])`. A client-provided device ID never suffices without a valid proof using the stored public key.

Successful responses are `{payload, signature}`, both base64url. The vendor signature covers the decoded payload bytes. Payload: `{version:1,licenseId,deviceId,type:'trial'|'regular',status:'active'|'revoked',issuedAt,expiresAt,challenge,revision}`. Times are UTC epoch milliseconds. Legacy active receipts last48 hours; subscription receipts have a shorter expiry if the subscription ends sooner. Revoked envelopes last48 hours for verification, but never grant access. No customer details or raw key appears in a receipt. Database batches enforce device capacity and record audits atomically.

The desktop accepts only matching vendor signature, device, fresh challenge, version, revision, and bounded timestamps. Admission happens on launch or successful sign-in/verification of a blocked session. Active verification resets the allowance of up to48 hours and10 offline launches, capped at subscription expiry. Unsigned HTTP errors never refresh access or count as confirmed revocation. Signed revocation is saved for the next launch while an admitted session continues until quit. Receipt expiry and exhausted offline allowances also take effect on the next launch; closing a project/window does not end an admitted session.

Collaboration uses the admitted host session and fresh host identity proofs so existing guests, reconnecting guests, and new guests can continue joining until the host quits. The desktop retains its last active receipt only in memory for those proofs; it stores the latest revoked receipt for the next launch. Keeping the app running can therefore defer enforcement indefinitely. An offline Mac cannot learn of revocation until it reconnects; until then, a later launch can still use its remaining offline allowance. Once that allowance ends, launching local projects requires a successful online check. Offline tampering resistance cannot make a user-controlled Mac fully tamper-proof.

Public API rate limits use atomic D1 counters keyed by an HMAC of the route and IP (12 activation attempts / 10 min, 120 verification attempts / min). Raw IPs and request bodies are not persisted or logged. Error responses use generic messages and `private, no-store`; there is no public license enumeration endpoint. The first activation requires internet. Server signing/DB outages return 503; a new app launch can use only the remaining offline allowance, while an admitted session continues until quit.

The signing key has a deliberately explicit release lifecycle: changing it requires distributing a desktop build trusting the replacement public key first. Existing builds cannot verify a new key automatically. Avoid rotating it without planning that transition. D1 rows and device keys are security-sensitive; protect backups and Cloudflare account access.
